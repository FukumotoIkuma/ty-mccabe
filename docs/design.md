# ty-mccabe の設計

## 目的

関数を分けても、分岐をほかの関数へ移しても下がらない McCabe の複雑度を出す。下げる方法は「分岐を減らす」か「まとまった単位を閾値以上の大きさで切り出し、それ自身の数で確かめる」だけにする。

道具がするのは、ty の答えで呼び出しのグラフを作り、そのグラフで複雑度を計算することだけ。グラフの情報は ty の公開の関数（言語サーバーが使うもの）と、可視性を上げただけの ty・ruff の関数（9）の答えだけから取る。Python の意味（どの構文がどの特殊メソッドを呼ぶか、継承の順など）を道具の側で写さず、ty の構造（推論の結果・キャッシュの型・推論の進み方）も変えない。ty が答えない所は数えず、8 に限界として書く。

## 1. 単位

複雑度を出す単位（グラフの節）は、ty の意味の索引（`semantic_index`）のスコープのうち、関数（`def`）とモジュールの最上位。

- クラスの本体は、それを書いた単位（モジュールの最上位か関数）の一部。メソッドは関数。
- 関数の中に書いた関数は、囲む関数（クラスを通り抜けて最も近い関数）と同じ組にする（3 の組）。
- lambda・内包表記は単位にせず、書いた単位の一部にする。

## 2. 単位の分岐の数

ruff の C901 の数え方（`get_complexity_number`。9 で可視性を上げる）を使う。C901 は、中に書いた `def` を「1 + その def の本体の分岐」として外に足す。これはその def の C901 の数と同じで、クラスの中に書いた def も足す。

- **関数**: C901 の数から、その関数だけの分岐を出す。C901 は、`ruff_linter` を同じコミットで組み込み、C901 だけを閾値 0 で掛けたもの（`# noqa` と範囲で抑えるコメントは効かせない）。関数だけの分岐 = C901 の数 − 1 − Σ（中に書いた def の C901 の数）。
- **モジュールの最上位**: モジュールの文に `get_complexity_number` を当てた数 − Σ（関数の外に書いた def の C901 の数）。

## 3. 複雑度

- 単位 u の複雑度 = u と、u から「閾値未満の単位」だけを通って辺を辿れる単位の、分岐の数の和 + 1。
- 閾値以上の単位への辺は 1 つの文として扱い、その先は数えない。閾値以上の単位は、それ自身の数で出る。
- 呼び合う単位の組（強連結成分。中に書いた単位は外の関数と同じ組）は、組を 1 つの単位として数える。呼ぶ先の組から順に決める。
- 閾値は引数で決める（既定 10。ruff の C901 の既定と同じ）。

この定義で、ty が辺を答えた範囲では、どの分岐も次のどちらかになる。

- 閾値以上のどれかの単位の数に入る。
- その分岐を辿れる範囲全体が閾値未満である。

## 4. 辺

単位の中の式・文を歩き、次の位置で ty に定義を聞く。答えが単位なら辺にする。中に書いた関数の本体はその関数の単位なので入らないが、デコレータ・引数の既定値と注釈・戻り値の注釈・型引数は、def を実行する外の単位に入る。

| 位置 | 聞く ty の関数 | 答え |
|---|---|---|
| 名前 | 定義への移動 `goto_definition` | 名前が指す定義（自分のプロジェクトの stub は実行時のソースへ写す）。呼ぶ所に限らない。関数を値として書いた所（コールバック・表に入れた関数・返した関数）も、書いた単位からの辺になる |
| 属性 | `ImplementationsFinder::for_attribute`（受け手がクラスのインスタンスでなければ定義への移動） | 受け手の型の継承の順で選ばれるメンバーと、受け手の型の下位のクラスでの上書き（兄弟のクラスは入らない）。property は、読む・書く・消すに応じて getter・setter・deleter |
| 属性で、クラスの本体で代入したメンバー（`m = f`・`p = property(f)`） | `binding_type`（9） | ty が代入に付けた型の関数、または property の accessor |
| 属性で、受け手の型が Protocol のインスタンス | `Type::is_assignable_to`・`to_instance_approximation`・`mro_member_definitions`（9） | 調べるファイルのクラスのうち、インスタンスを ty が Protocol へ代入できると答えたクラスで、ty が継承の順で選ぶ同じ名前のメンバー（基底から継いだものも）。Protocol の実装は、クラスを定義した単位でなく、使う側で数える（下位のクラスの上書きと同じ） |
| 二項演算子・単項演算子（`not` も） | `definitions_for_bin_op`・`definitions_for_unary_op` | ty が演算子で呼ぶと決めた特殊メソッド |
| 呼び出し | `call_signature_details` | 呼ぶものの定義。クラスならコンストラクタ（`__init__`・`__new__`）、呼ぶ値の型が関数の共用型なら要素それぞれ |
| 呼び出しで、呼ぶ値の型が関数 | `FunctionType::definition`（9） | overload の関数なら実装（ty が呼び出しで答えるのは overload の宣言） |
| クラスのパターン `case C(x=1)`・`case C(1)` | `ImplementationsFinder::for_attribute`、位置は `class_pattern_positional_sources`（9） | パターンが読む `C.x`。位置で照らす属性の名前は、ty が `__match_args__`・dataclass の欄から答える |
| import する名前のドットで区切った部分 | 定義への移動 | モジュール（そのモジュールの最上位への辺）。`from . import x` の x がサブモジュールなら、そのモジュール |
| `from . import x`（モジュールを書かない相対の import） | `SemanticModel::resolve_module` | その段のパッケージ |
| `from m import *` | `static_dunder_all`・`definitions_for_imported_symbol` | ty が静的に読める m の `__all__` の名前（サブモジュールなら、そのモジュール） |
| モジュールの最上位 | `file_to_module`・`ModuleName::parent`・`resolve_module` | 親のパッケージ（Python はモジュールを実行する前に親のパッケージを実行する） |

名前・属性・呼び出しの答えは関数の単位だけを、import の答えはモジュールの最上位だけを、辺の先にする（モジュールの名前を書いても、そのモジュールを実行しない）。

ty は、変えられるコンテナ（辞書・リスト）に入れた関数の型を、呼べるものの型（`Type::Callable`）に広げる。その要素を呼ぶ所（`table[k]()`）は、どの関数かを ty が決めていないので辿らない。関数は、表に名前を書いた単位で数える。

実装への移動（`goto_implementation`）は、プロジェクトのすべてのファイルを見る。辺の先は調べるファイルのメソッドの単位だけなので、同じ `ImplementationsFinder` を、同じ名前のメソッドの単位があるファイルについてだけ引く。答えは、受け手の型・名前・読むか書くか消すかの組ごとに覚える（`for_attribute` はこの 3 つだけで答えを決める）。

## 5. 出力

- 何も付けないとき: 分からない所と、数の要約だけを出す（CI 向け）。
- `--list`: 閾値以上の単位を、大きい順に出す。行は「複雑度・単位だけの複雑度（関数は C901 と同じ）・ファイル:行 名前」。名前は、外の関数・クラスの名前をドットでつないだもの。モジュールの最上位は `<module>`。
- `--all`: すべての単位を出す。
- `--explain <単位>`: その単位の数に入れた単位と、それぞれの分岐の数を出す。分からない所も出す。
- 分からない所: 属性で、受け手の型を ty が Any・Unknown と答えたもの（共用型の要素にあるものも。`HasType::inferred_type` が `Type::Dynamic`）。行は `分からない（受け手の型が分からない）: ファイル:行 属性の式（単位 の中）`。
- 終了コード: 分からない所が無ければ 0、あれば 1、道具が動けなければ 2（読めないファイル・読めないディレクトリ・構文の誤り・UTF-8 でない引数など）。

## 6. 数を下げる方法

| 操作 | 数への効き方 |
|---|---|
| 分岐を減らす | 下がる |
| 閾値以上の単位を切り出す | 元の単位から切り出した分が抜ける。切り出した単位はそれ自身の数で出る |
| 閾値未満の関数・メソッドに分ける（呼ぶ所を ty が答えるもの） | 呼ぶ側へ展開されて元に戻る |
| 分岐を、ty が呼ぶ先を答えない所へ移す（8） | 使う側から抜ける。移した先は、それ自身の数で出る |

閾値以上の単位を確かめた（Lean で証明した、テストで固めた）かどうかは、道具は扱わない。道具が出す閾値以上の一覧が「確かめる単位の一覧」で、確かめたかどうかは使う側が別に確かめる。

## 7. 測った時間

型推論は、`ty check` と同じく、ファイルを rayon で並べ、ジョブごとに ty のデータベースを複製して回す（ty_project の `map_with_db`）。

ある非公開の Python のプロジェクト（708 ファイル、単位 4571）で、`--threshold 5` のとき、8 コアの機械で全体が 3.3 秒（CPU 6.9 秒）かかる。型推論が 1.1 秒、辺が 2.0 秒。

| 段階・問い合わせ | 時間 |
|---|---|
| 型推論（並べたとき。1 本で回すと 3.2 秒） | 1.1 秒 |
| 辺: 名前（`goto_definition`、10.9 万回） | 0.54 秒 |
| 辺: 属性（2.8 万回。うち Protocol 0.40 秒、下位のクラスの探索 0.09 秒） | 0.82 秒 |
| 辺: 呼び出し（2.3 万回） | 0.41 秒 |
| 辺: 演算子・import ほか | 0.23 秒 |

- 型推論のうち、診断を作る分は命令の約 2% で、省いても効かない。
- 下位のクラスの上書きを、属性の組ごとに調べるファイルのすべてで引くと、辺だけで 24.8 秒かかった。同じ名前のメソッドの単位があるファイルだけを見ると、答えは同じで 0.09 秒になる。

## 8. 受け入れた限界

ty が呼ぶ先を答えない所は、辺にしない。そこへ移した分岐は使う側の数に入らず、移した先の単位の数で出る。道具の側で Python の意味を写して補わず、ty の推論に手を入れて答えを取り出すこともしない。ty の答えが増えれば、そのまま数に入る。

迂回の例（`tests/fixture/evade/`）では、限界に当たる例の行に、本来の数（`期待`）と今の数（`限界`）と理由を書く。テストは今の数と照らすので、ty の答えが増えて数が変われば落ちる。そのときは限界を書き直す。

- **暗に呼ぶ特殊メソッド**: 比較・`in`・真偽の判定（`if x:`・`match` のガード・内包表記の `if`）・`for`・内包表記の `for`・`yield from`・`*x`・`with`・添字（読む・書く・消す。クラスの添字の `__class_getitem__` も）・`+=`・`await`・f 文字列・値のパターン（`case 1:` の `==`）。ty は推論の中でこれらを解くが、呼ぶ定義の記録（`Bindings`）をその場で捨て、公開の関数でも答えない（二項・単項の演算子だけは答える）。
- **組み込みの関数が中で呼ぶ特殊メソッド**: `len(x)` の `__len__`（クラスの値なら metaclass の `__len__`）、`str(x)` の `__str__`、`round`・`min`・`zip`・`filter`・`list`・`reversed`・`isinstance`（metaclass の `__instancecheck__`）・`copy.copy` など。ty は組み込みの関数を typeshed の関数として解くだけで、中で呼ぶ特殊メソッドを答えない。
- **記述子の `__get__`・`__set__`、`__getattr__`**: ty が解くときに `Bindings` を捨てる。Protocol を `__getattr__` で満たすクラスも、ty が継承の順で選ぶメンバーが無いので辿らない。
- **`+=` の属性**: `x.p += v` は、ty が属性を書く所としてだけ答えるので、getter で読むことを辿らない。
- **演算子の特殊メソッドの、下位のクラスでの上書き**: ty の `definitions_for_bin_op`・`definitions_for_unary_op` は、受け手の型の特殊メソッドだけを答える。
- **下位のクラスが、受け手の型でない別の基底から継いだメソッド**（`class Child(Mixin, Base)` の `Mixin.m`）: ty の実装への移動は、メソッドを自分で書いた下位のクラスしか答えない。
- **stub のクラスを受け手の型にした所の、下位のクラスでの上書き**: ty の実装への移動は、stub のクラスから実行時のソースの下位のクラスを探さない。
- **コンストラクタの overload と、代入した overload の関数**: ty は呼び出しで overload の宣言だけを答える（関数の値を呼ぶ所は、ty の関数の型から実装を引く）。
- **metaclass の `__call__` と、metaclass の `__match_args__` の property**: ty が答える形が無い。
- **デコレータを当てる呼び出し**: `@d def f` で ty が答えるのは d の式。d を当てる呼び出しが呼ぶもの（`@D()` が作った値の `__call__`、`@C` の `__init__`）と、d が受け取った f を中で呼ぶこと（値の流れ）は数えない。
- **stub が属性として宣言したサブモジュール**: ty の定義への移動が属性の宣言を答えるので、import しても、そのモジュールへ辺を引かない。
- **Protocol を満たすクラス・下位のクラス**: 実際にその値が渡されなくても、満たすクラスと下位のクラスの実装を数えるので、多めに数えることがある。
- **分からない所**: 出すのは、受け手の型を ty が Any・Unknown と答えた属性だけ。名前を文字列で引く所（`getattr(x, "m")`・`getattr(x, name)`・`globals()`・`__dict__`・`eval`・`importlib.import_module`）は、ty に見分ける区別が無く、関数の一覧を道具が持つと自作の決まりになるので、辿らず、出さない。
- **分岐の数え方は ruff の C901**: 条件式（`a if c else b`）・内包表記の `if`・`and`・`or`・`assert` は分岐に数えない。`if` を条件式に書き換えると数は下がる。

## 9. ty・ruff に当てるパッチ

ty・ruff の中にすでにある関数の可視性を上げる（`pub` にする）だけのパッチ（`patches/ty.patch`）を、Cargo.toml の rev の ruff に当てて使う（`scripts/prepare_ty.py` が `vendor/ruff` に用意し、Cargo.toml の `[patch]` がそこを使う）。関数の中身・型・キャッシュ・推論の進み方は変えない。

| 関数 | 何に使うか |
|---|---|
| ruff の `get_complexity_number`（と、それを含むモジュール `rules`・`function_is_too_complex`） | モジュールの最上位の分岐の数（2） |
| ty の `FunctionType::definition` | overload の関数の実装 |
| ty の `class_pattern_positional_sources`・`ClassPatternPositionalSource`（と、それを含むモジュール `match_pattern`） | クラスのパターンが位置で読む属性 |
| ty の `binding_type` | クラスの本体で代入したメンバーの関数・property |
| ty の `Type::to_instance_approximation` | Protocol を満たすかを聞く、クラスのインスタンスの型 |
| ty の `mro_member_definitions` | Protocol を満たすクラスで、継承の順で選ばれるメンバー |

ty の版を上げてパッチが当たらなければ、版の追従は PR を開いて止まり、人がパッチを直す。
